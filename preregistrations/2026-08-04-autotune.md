# AUTOTUNE — can a fixed-budget overnight flag search beat the planner's own advice?

**Date staked:** 2026-08-04, before any tuner code exists and before any config was measured.
Inspired by karpathy/autoresearch's harness discipline (fixed wall-clock budget per experiment,
single reviewable output file, keep/discard by one metric), applied to llama.cpp flag-space
instead of train.py-space — with the honesty layer that pattern is missing: every candidate is
PRICED BY THE LAW before it runs, and every predicted-vs-measured disagreement is calibration
food, not noise.

**The claim under test:** an unattended, deterministic, fixed-budget search over llama.cpp
runtime flags finds a config materially faster than `quantprobe plan`'s emitted command on at
least one frontier row of this box — OR the planner is already within noise of a 100-config
search, which is a publishable result about the planner, not a failure.

## Design

- **Search space (runtime flags only; model file and placement family fixed per row):**
  `-t` {4,6,8}, `-ub` {256,512,1024,2048}, `-b` {512,2048}, KV `-ctk/-ctv` {f16,q8_0},
  `-ngl` {planned−2 … planned+2}, `-fa` {on,off}, `--no-mmap` {on,off}, and for the MoE row the
  `-ot` resident-expert regex variants the planner already knows. Enumerated deterministically,
  seeded; the law prices every candidate it CAN price first, and the sweep runs best-predicted-
  first so early stopping favors the model's ranking being right.
- **Fixed budget per config:** llama-bench `tg64, r=2` under a 180-second wall cap (load
  included). A config whose load alone busts the cap is recorded as `over-budget`, not skipped
  silently. ~100 configs a night.
- **Rows (the frontier trio):** 0.6B all-in-VRAM, 7B all-in-VRAM, 30B-A3B split.
- **Output:** ONE reviewable artifact per row — the winning flags line plus the full
  (config, predicted, measured) ledger. The autoresearch single-file principle, applied to advice.

## Staked gates

- **P1 (the product claim):** best-found ≥ **+10%** measured tok/s over the planner's emitted
  config on ≥1 of the 3 rows. If NO row clears +10%, the published headline is the inverse and
  equally valuable: *"a 100-config overnight search failed to beat `quantprobe plan` by 10% —
  the planner's advice is near-optimal for this box."* Either way a claim ships.
- **P2 (does the law rank, not just point-estimate):** Spearman rank correlation between
  predicted and measured tok/s over the priceable subset of each row ≥ **0.5**. Below that, the
  best-predicted-first ordering is decoration and must be dropped from the tool.
- **KR-A (anti-noise):** any config claimed as a winner must reproduce its gain at `r=3` in a
  fresh server session, same machine state, before it is published. No reproduction, no claim.
- **KR-B (state):** one machine state per row (C-14), mkdir-or-refuse lock shared with every
  other runner, arms sequential, GPU state logged before/after each row. Overlap-window data is
  deleted, never explained.
- **KR-C (scope honesty):** flags the law cannot price (`-t`, `-fa`, mmap) are measured but
  their predicted column is `null` — a null is not a prediction and is excluded from P2. The
  tuner may not silently extend the law's claimed coverage.
